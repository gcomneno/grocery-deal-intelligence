# Evidence-aware proposal contract

## Status

Design decision for Issue #47. No runtime behavior changes are introduced by this document.

## Decision

Grocery Deal Intelligence needs a proposal contract that is semantically distinct from the canonical Grocery Offer contract.

Canonical principle:

> A proposal represents only claims the AI proposes from the evidence available to it. It need not be complete, it is not canonical, and absence of a field is valid information.

Consequences:

- absence is not an error;
- absence is not a fabricated `null` claim;
- proposal validity is not canonical validity;
- proposal completeness is not canonical completeness;
- AI output remains advisory;
- only deterministic processing may grant canonical authority.

## Why the canonical schema cannot also be the proposal contract

The fixed real-retailer experiments established two facts.

First, schema-constrained inference greatly improved structural conformance. Second, constraining AI output directly to the complete canonical schema pressures the model to populate canonical-required structures even where source evidence is absent.

Prompt-only instructions to omit unsupported claims did not provide a reliable control boundary: on the fixed corpus, unverifiable claims increased from 29 to 36 while contradicted claims remained zero.

The problem is therefore contractual rather than merely prompt-related.

## Semantic model

A proposal is a partial mapping of canonical-addressable claims.

A field present in the proposal means:

> the AI is making this claim and the deterministic verifier must evaluate it.

A field absent from the proposal means:

> the AI makes no claim about this fact.

Absence MUST NOT be interpreted as false, contradicted, empty, or canonical `null` unless the canonical field itself explicitly has that meaning.

The proposal contract SHOULD prefer omission over an explicit `unknown` marker. An explicit unknown state is justified only when the distinction between “no claim made” and “AI explicitly determined that the value is unavailable” is required by a future use case. No such requirement has yet been demonstrated.

## Minimal contract

The first implementation SHOULD use a grocery-owned partial JSON object whose field names and nested paths correspond to canonical claim paths, but whose fields are optional unless required solely to make the proposal representation itself unambiguous.

Example:

```json
{
  "retailer": "esselunga",
  "product_name": "FORST V.I.P. Pils CAN 3 x 0,33 l",
  "price": 1.83,
  "validity": {
    "from": "2026-08-24T00:00:00Z",
    "to": "2026-09-20T00:00:00Z"
  }
}
```

This proposal makes five claims. It makes no claim about locality, provenance, verification, or promotion metadata not represented in the object.

Nested objects MAY themselves be partial. Empty nested objects SHOULD be rejected or normalized away because they make no claim.

The proposal contract MUST NOT include an `is_canonical`, `validated`, `verified`, `eligible`, confidence-to-authority, or similar field that could imply authority.

## Representation choice

A distinct grocery-owned JSON Schema is recommended for the first implementation, but only as a serialization/shape constraint for this semantic contract.

The schema is not the architectural decision; the semantic distinction is.

Reasons to use a proposal JSON Schema:

- GiadaWare AI already supports schema-constrained JSON;
- it can constrain types without requiring canonical completeness;
- it preserves the provider-independent boundary;
- it gives deterministic validation of proposal shape before claim verification;
- it is easy to version independently from Grocery Offer v0.1.

The proposal schema MUST NOT be generated by mechanically removing `required` from the canonical schema. It should be deliberately defined and versioned as a separate contract.

## Deterministic flow

```text
raw retailer source
        ↓
deterministic source-evidence projection
        ↓
AI proposal constrained by proposal contract
        ↓
deterministic proposal-shape validation
        ↓
deterministic claim verification
        ↓
deterministic candidate-to-canonical projection
        ↓
canonical Grocery Offer validation
        ↓
canonical admission policy
        ↓
canonical dataset
```

### Proposal-shape validation

This validates only the proposal contract: known paths, JSON types, allowed enums, and representation rules. It does not establish source truth or canonical eligibility.

### Claim verification

Every claim actually present in the proposal is compared with deterministic source evidence and classified using the existing support semantics where applicable:

- `supported`;
- `contradicted`;
- `unverifiable`.

An absent claim produces no verification result.

### Candidate-to-canonical projection

Projection is deterministic and is the only component allowed to assemble a complete canonical candidate from proposal claims plus deterministic evidence/defaults whose semantics are explicitly defined by Grocery Deal Intelligence.

Projection MUST NOT invent missing facts and MUST NOT perform retailer-specific post-inference repair.

If required canonical information cannot be established, projection returns an incomplete/not-projectable result rather than fabricating a value.

### Canonical validation and admission

The existing canonical schema and deterministic admission authority remain downstream and unchanged in meaning.

A proposal can therefore be valid while not projectable to canonical. A projected candidate can be structurally invalid. A structurally valid candidate can still be admission-ineligible.

## Ownership and provider boundary

Grocery Deal Intelligence owns:

- proposal semantics;
- proposal schema/version;
- deterministic evidence projection;
- claim verification;
- proposal-to-canonical projection;
- canonical validation;
- admission policy.

GiadaWare AI owns only provider-independent execution of the requested schema-constrained inference. Ollama/Qwen remain implementation details behind GiadaWare AI.

## Compatibility and migration

Migration SHOULD be incremental.

1. Add Proposal v0.1 schema and deterministic proposal validation without changing current ingestion behavior.
2. Add proposal-oriented capability/adapter support alongside the current canonical-shaped proposal path.
3. Add deterministic proposal-to-canonical projection and tests.
4. Run the same fixed four-record corpus through both paths and compare structural validity, support classifications, admission, canonical count, and total emitted claims.
5. Only after evidence supports the new path, make it the preferred admission-enabled AI ingestion route.
6. Retire the old direct-canonical AI proposal path separately; do not silently redefine it.

## Required invariants

The implementation must preserve:

```text
proposal validity != source truth
source support != canonical validity
canonical validity != admission eligibility
AI proposal != canonical authority
```

and:

```text
known deterministic fact -> may be grounded and deterministically projected
AI-present claim -> must be verified
AI-absent claim -> no claim
missing required canonical fact -> projection/admission failure, never fabrication
```

## Explicit non-goals

This decision does not:

- change Grocery Offer v0.1;
- weaken canonical validation;
- change the current admission policy;
- add retailer-specific repair;
- treat `unknown` as a magic placeholder;
- ask AI to judge its own correctness;
- make confidence scores authoritative;
- change GiadaWare AI provider/backend contracts.

## Follow-up implementation sequence

Recommended sequence:

```text
Proposal v0.1 contract + validator
        ↓
proposal-oriented AI capability/adapter
        ↓
deterministic proposal-to-canonical projection
        ↓
fixed-corpus comparative experiment
        ↓
evidence-based migration decision
```
